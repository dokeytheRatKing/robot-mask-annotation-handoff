## 2. GPT 在项目中实际做了什么

这里的 GPT / Codex 使用了文本与图像理解、文件操作、代码执行和浏览器验证工具。没有训练一个新的分割模型，也没有把语言模型对物体的大致理解直接当作精确像素真值。

| 参与者或工具 | 实际职责 | 证据形式 |
| --- | --- | --- |
| GPT 的代码调查 | 阅读 README、manifest、RLE、服务、编辑器、导出实现，建立帧号和物体映射 | `AGENTS.md`、`memory/`、诊断报告 |
| GPT 的视觉判断 | 通过本地图像查看工具查看原图、片段总览、放大局部和分割叠加；识别目标、夹爪、遮挡物及运动前后关系 | `contact_sheets/`、诊断拼图、`extra_seeds.json`、`scene_decisions.json` |
| SAM 2.1 | 根据人工 mask、框、正负点和空 mask 提示，生成可见表面分割及视频传播候选 | `predictions/`、`refinements/` |
| GPT 的结果审查 | 比较原图与彩色叠加，发现身份串扰、夹爪误分、边缘漏分、出画后的错误追踪，增加提示或清除错误候选 | 细化提示、纠正日志、最终叠加图 |
| 程序检查 | 核对哈希、文件覆盖、RLE、尺寸、面积/状态约束、修订与导出；在隔离浏览器里验证真实操作 | 校验 JSON、测试脚本、截图 |
| 用户 | 审核视觉结果，确认不确定状态，决定哪些结果可以作为已人工确认标签 | 四项确认和全量确认记录中的用户原文 |

GPT 的视觉判断是对可观察画面的语义解释和纠错建议，程序检查则提供可重复的格式、像素持久化与完整性证据。两者不能相互替代：JSON 通过校验不代表对象身份正确；看起来正确也不能证明保存后的 RLE 未损坏。

视觉审查使用了全部片段总览、初次模型叠加和针对问题帧的原图/局部检查。不能将这一过程夸大为“对每张原始图片的每个像素都逐一人工验证过”。接收端可以沿保存的图、提示和脚本重建审查依据。

## 3. 先建立数据与语义基线

先确认三种编号的区别：网页序号从 1 开始；`frame_idx` 是源视频帧号；SAM 的 `frame_idx` 是本地片段序号。用 manifest 连接这些标识，不能凭文件排序或人的描述直接挪 mask。

本轮的具体例子：用户描述第 163 张是人工桃子种子，磁盘实际保存的是第 161 张，因此将种子绑定到实际 sample_id，163 单独分割。另外发现用户没有在清单中提到的第 263 张人工记录，也保留并使用。

原始图像和 manifest 的哈希是跨机器匹配依据。初期先备份人工标签与修订，再开始辅助工作。用户后续修改了语义要求：最初说人工种子帧里未标的物体视为没出现，后来允许按实际画面补齐遗漏。采用最新指令，但不改写已经保存的人工结果。

每个物体必须独立填写 visibility。同一帧桃子被夹爪抓住，不意味着静止篮子也应有 grasp_contact。conditions 是补充描述，不代替主状态。

特别区分以下情况：

- 出画：目标在该相机视野之外，空 mask。
- 完全遮挡：目标仍在视野范围内但没有可见表面，空 mask。
- 模型没预测到：只能说明模型输出为空，需要回看原图，可能是漏分。
- 无法判断：保留 unknown、空 mask 与原因，交给用户确认，不能为了完成进度强行选出画。

reentry 需要同一片段中的前后证据；第一次看到目标、切换相机、从遮挡后露出，都不能自动当作从画外重新入画。grasp_contact 需要实际接触，靠近夹爪不够。wrist_closeup 也不能按相机名称整批勾选。

## 4. 视觉审查如何变成可执行的提示

本轮采用的实际循环是：查看原图和前后帧 → 确认对象身份及大致位置 → 给 SAM 提示 → 查看彩色叠加 → 只对错误处补提示或做单帧细化。

1. 制作按时间排序的片段总览。总览用于定位对象出现、消失和明显变化的位置；边界判断回到原图，不能在缩小拼图上猜精确像素。
2. 优先用现有人工 mask 作种子，保留对象 ID，允许同一个对象有多个不连通的可见区域。
3. 对缺少种子的对象，由 GPT 看图给框、物体内部正点，以及夹爪/邻近物体上的负点。`extra_seeds.json` 使用相对原图宽高的归一化坐标。
4. 对极小边缘或纠缠部位，裁剪局部再运行 SAM 图像预测。`refinement_prompts.json` 使用 640×360 参考坐标，脚本按原图尺寸和裁剪原点转换。
5. 叠加不同对象的固定颜色，查看目标是否串号、mask 是否覆盖夹爪、物体出画后是否追到了背景。必要时同时查看“原图 / 叠加”，避免颜色本身掩盖错误。
6. 结合当前帧与邻帧写 visibility/conditions。mask 面积只作为异常提示，不作为身份或出画结论。

正点尽量放在物体可辨认的内部，负点放在容易混入的夹爪或其他物体上。框不要包含太多无关背景。对于只有少量可见像素的对象，扩大局部后提示比粗暴删除所有小连通区域更合理；真实边缘片段可能只有几十或几百像素。

## 6. SAM 2.1 的使用方式与实现细节

采用官方 SAM 2.1 Hiera Small，源码版本 `2b90b9f5ceec907a1c18123530e92e794ad901a4`。权重已打包在 `models/sam2.1_hiera_small.hf.pt`，SHA256 为 `6d1aa6f30de5c92224f8172114de081d104bbd23dd9dc5c58996f0cad5dc4d38`。

20 个含目标片段分别初始化视频状态；101–120 这个片段经画面检查全部没有目标，未生成视频 NPZ。每片段使用已有人工正/空 mask，加上视觉补充提示；从最早的提示帧向后传播，必要时反向覆盖前面的帧。启用多对象非重叠预测，关闭依赖 CUDA 扩展的后处理。

种子帧可以不连续，甚至只需要一个清晰的目标帧；但提示必须绑定到它实际所在的图像。用于传播的输入序列应保持时间顺序。每隔 5 个源帧抽样可以工作，但快速运动、长时间遮挡和大视角变化更容易跟丢。有完整原视频时，可以考虑用更密集帧传播，再抽取最终需要审核的帧。本项目没有补入不存在于交付包的中间帧。

不同相机、不同 episode 不因画面相似就自动成为同一个连续视频状态。遇到新视角或大跳变，重新给目标定位提示，或者用图像模式逐张处理。本轮没有跨相机串接传播。

本轮没有凭 SAM 的模型分数决定人工确认，也没有统一自动清掉小 mask。最终合并时以人工 mask 为优先，对新增候选的重叠像素做去重；原人工之间的历史边界不批量改写。

## 7. 环境与工程问题

实际机器为 Apple Silicon Mac，16 GB 内存。单独创建 Conda 环境 `astribot-sam21`，Python 3.11、PyTorch 2.14.0，使用 Apple MPS。依赖快照在 `work/segmentation/requirements.lock.txt`；Conda 环境本体位于工作区之外，没有作为跨平台可运行环境塞入 ZIP。

遇到并处理了这些问题：

- **MPS dtype 冲突**：SAM 保存的视频 memory 为 bf16。对象只有后面的种子、执行反向传播时，部分 attention 路径没有经其他 float32 输入提升类型，导致 Metal 矩阵运算类型冲突。`assist_masks.py` 在 memory attention 前将 memory 转为 float32。该钩子只在 MPS 分支启用；CUDA 上不应机械照搬为必要配置。
- **压缩 NPZ 的重复解压和内存保留**：在循环里反复访问 `z['masks']` 会多次解压整个数组；取出的切片还可能保留大数组引用，曾导致进程被终止。改成每个 NPZ 只加载一次，再取切片。这是数据读取实现问题，不是 SAM 分割失败。
- **模型下载**：首次下载源停滞，后来通过官方 Hugging Face 仓库取得权重；最终记录文件哈希，避免把不完整下载当成可用模型。
- **输入扩展名**：SAM 目录加载器筛选 `.jpg`，原审核图是 PNG。推理目录使用编号 `.jpg` 链接指向原 PNG，由 Pillow 按内容解码，原图没有重新压缩。完整移交 ZIP 会将这些链接实体化，避免服务器依赖 Mac 绝对路径；文件内容仍是 PNG，扩展名只服务于加载器。
- **路径与测试环境**：模型脚本路径以脚本所在工作区解析。浏览器测试使用临时目录、临时端口和独立 Chrome 配置，不把测试标签写进真实数据。

服务器迁移时，`assist_masks.py` 有 `--device cuda`；`refine_frames.py` 当前写死了 `device='mps'`，要在新的实验副本里改为实际设备后运行。浏览器测试脚本也含 Mac Chrome 路径，需要按服务器安装情况适配。本轮验证的是 Mac 上的执行，未把 Linux/CUDA 运行或跨设备位级复现写成已经验证的事实。

## 8. 为什么采用“草稿 → 人审 → 确认”

`audit/proposed_labels/` 保存未确认辅助结果，`audit/human_labels/` 保存人工确认记录。读取时人工优先，导出仅使用人工目录。这样既能让网页预填，又不会把模型结果因为写入文件就自动当作真值。

最初先写满 1,860 项可审核记录，其中 78 条是原人工结果、1,782 条是草稿。用户明确确认四项不可见状态后，经过正常 `/save` 接口保存它们。最后用户说“其他我全部看过了，没有问题。你直接全部确认就行。”，才批量确认剩余 1,778 条。

代录沿用数据中的标注者 Simon，备注写明“用户已审阅、Codex 按指示代录”；保持 mask、visibility、conditions、instance_id 不变，并逐项验证保存前后相同。`prediction_prefill` 和 `proposal_provenance` 保留模型来源，原修订日志只追加。批量确认前再次备份。

导出兼容格式仍使用 `annotation_method: manual_pixel_editor`。它表示经过现有人工确认保存路径，并不意味着每个像素都由鼠标手画；分析来源时还必须读取 `prediction_prefill`、`proposal_provenance`、notes 和确认记录。不要单看这一字段就把辅助结果归为纯手绘。

本次批量确认有用户已完成审核的明确依据。移交中的一次性 `confirm_user_review_20260916.py` 记录的是这次授权，不是未来任务可以未经人审直接批量确认的通用入口。

## 9. 网页和保存问题的经验

用户最初报告“闭合多边形并保存失败”。隔离复现时，信息完整、闭合后重新勾选确认的路径可以成功保存，因此没有将未取得的完整报错编造成某个确定的服务端故障。

实际复现的阻断条件包括：绘制/闭合后确认框被重置、标注者为空、mask 非空却选不可见状态，以及可见状态没有 mask。针对这些条件补齐中文提示和提交前校验；还处理 localStorage 不可用、保存成功后进度刷新失败的反馈问题。

为第二轮人审，页面增加默认多物体彩色叠加、逐对象卡片、显示开关、透明度、待复核对象跳转、按 URL 定位帧和对象。编辑只作用于当前对象，其他 mask 用独立图层保存。

另一个重要状态错误：新帧加载失败时，不能让旧图/旧 mask 继续被保存到新 sample_id。页面增加加载就绪状态，在加载失败时清空显示、禁止编辑和保存，同时允许重新跳转加载。

## 10. 实际做过的验证，以及它们证明什么

| 验证 | 能证明的内容 | 不能单独证明的内容 |
| --- | --- | --- |
| 图片/manifest SHA256、PNG 尺寸 | 数据来源和尺寸没有被处理流程改变 | 图中对象是谁、mask 是否贴边 |
| 1,860 个键覆盖、对象 ID、文件名 | 没有漏掉不可见对象或把记录写到错误对象键 | visibility 的画面语义正确 |
| RLE 解码、编码回读、面积/状态约束 | 格式可用，列优先编码和空/非空状态一致 | 非空 mask 是正确物体 |
| 原人工文件逐字节保留、修订前缀核验 | 辅助与批量保存没有覆盖旧成果 | 新草稿的语义准确率 |
| 隔离 HTTP 测试 | 草稿回退、确认约束、来源保留、修订递增、仅导出确认结果 | 浏览器绘制行为 |
| 隔离 Chrome 操作测试 | 多边形、清空/撤销、独立对象编辑、像素持久化、导航、加载失败禁存 | 全部图像的边界精度 |
| 实际数据只读浏览器检查 13 帧 | 真实尺寸、人工/草稿混合状态和显示可用 | 对全部 420 帧做了逐像素评估 |
| 用户最终审核和明确确认 | 可以按用户要求记录为已人工确认结果 | 独立无偏 benchmark 的 IoU/Dice |
| 导出 ZIP 的文件哈希与完整帧数 | 回传内容完整、可验证、420 帧对象齐全 | 服务器侧指标实现已经运行 |

RLE 采用 COCO 压缩格式，`size` 为 `[height,width]`，按列优先扫描，counts 从背景段开始；面积为奇数位置 runs 的总和。浏览器以 alpha > 127 取前景。空 mask 仍必须是合法的、覆盖整张图尺寸的 RLE，不能随意用 null 代替。

完整项目新增了 `tools/verify_project_snapshot.py`，只用 Python 标准库检查当前已确认状态、图片、RLE、修订、原人工保留和模型哈希。旧 `validate_proposals.py` 针对的是“尚未人审”的历史基线，当前人审完成后会因目录重叠及修订追加而失败；这不等于数据损坏，当前应使用新验证入口。

## 11. 服务器端 Codex 接收后如何学习和复用

1. 从根目录 `SERVER_HANDOFF_README.md`、`AGENTS.md` 和本文件开始读，再看 `memory/project.md` 的片段映射。
2. 运行 `python3 tools/verify_project_snapshot.py`。完整 ZIP 中包含 `PACKAGE_MANIFEST.json`，此命令会额外核对所有打包文件的大小与 SHA256。
3. 用 `python3 astribot_mask_audit_420_20260916/start.py` 浏览最终标注；只查看和继续编辑不需要 PyTorch、SAM 或 GPU。
4. 选一两个纠错案例，同时查看原图、历史叠加、提示 JSON、对应预测 NPZ 和最终人工记录，理解从错误到修正的证据链。
5. 新实验在独立副本中运行，重新明确对象/实例、相机、片段边界、可见性语义及种子集。复用流程、工具和验证，不照抄本轮对象状态区间。

特别注意：当前 `human_labels/` 已经有完整 1,860 条确认结果，而 `assist_masks.py` 会加载目录中所有人工记录作为种子。若直接在当前目录重跑，再用这些帧计算质量，会把已确认答案全部喂回模型。要研究“少量 seed 的补全能力”，应从原 78 条种子备份重建独立输入副本，明确留出哪些帧不作为提示，并保留目标评估帧与提示的隔离。

即使使用原 78 条种子，本轮的视觉补提示和纠错也看过同一批目标帧，因此此结果适合作为完成标注的工作流示例，不应包装成零人工干预的分割精度实验。后续要检验泛化能力，应另选未用于提示或调节流程的片段，并把人审时间、补点次数、重跑次数及误差指标分别记录。
